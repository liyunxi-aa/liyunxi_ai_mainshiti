🕸️ LangGraph · Agent 状态图编排框架

将 LLM Agent 建模为有向状态图（StateGraph）— 节点是计算步骤，边是条件转移，支持循环、分支、并行、检查点与人机协作

1. StateGraph 核心抽象：节点 + 边 = Agent

LangGraph 将 Agent 应用建模为一张 有向图 G = (V, E)： 节点（Node） 是执行计算的函数（调用 LLM、执行工具、处理结果）， 边（Edge） 定义节点间的转移规则（普通边 / 条件边）。 整个图共享一个 State（TypedDict），沿边传递并在每个节点被更新。

💡 图 vs 链的本质区别：LangChain 的 Chain（RunnableSequence）是有向无环图（DAG），数据只能单向流动。 LangGraph 的 StateGraph 允许循环——这正是 Agent 需要的： 模型思考 → 调用工具 → 观察结果 → 再次思考 → ...，直到任务完成。 循环是 Agent 自主性的核心。

2. ReAct Agent 循环 — 最经典的 Agent 图模式

ReAct（Reasoning + Acting）是最基础的 Agent 模式。在 LangGraph 中， agent 节点调用 LLM 决定下一步动作，条件边检查是否有 tool_calls： 如果有 → 进入 tools 节点执行；如果没有 → 直接 END。 tools 节点执行完毕后无条件回到 agent 节点，形成循环。

# LangGraph 构建 ReAct Agent
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # 自动追加而非覆盖

# 1. 定义节点函数
def call_model(state: AgentState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}

# 2. 定义条件边逻辑
def should_continue(state: AgentState) -> Literal["tools", "__end__"]:
    last_msg = state["messages"][-1]
    if last_msg.tool_calls:
        return "tools"     # 继续循环
    return "__end__"         # 结束

# 3. 构建图
workflow = StateGraph(AgentState)
workflow.add_node("agent", call_model)
workflow.add_node("tools", ToolNode(tools))
workflow.set_entry_point("agent")
workflow.add_conditional_edges("agent", should_continue)
workflow.add_edge("tools", "agent")  # 无条件回到 agent

app = workflow.compile()
💡 条件边 = Agent 的"大脑"：should_continue 函数就是 Agent 的决策路由。 它检查 LLM 返回的消息中是否包含 tool_calls（模型决定调用工具）还是普通文本（模型认为任务已完成）。 这个简单的二分逻辑支撑了所有单 Agent 应用。更复杂的场景可以路由到多个不同的工具节点甚至多个不同的 Agent。

3. 条件路由 — 多意图分发

LangGraph 的条件边不仅可以判断"继续/停止"，还可以根据状态将请求路由到多个不同的节点。 典型的 Supervisor / Router 模式：一个 supervisor Agent 分析用户意图， 将任务分发给不同的专业子 Agent（如：客服、搜索、数据分析），各子 Agent 独立执行后返回结果。

from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, END
from langchain_core.messages import BaseMessage
from langchain_core.utils.function_calling import add_messages
from langchain_openai import ChatOpenAI

# ======================
# 1. 定义路由决策结构
# ======================
class RouteDecision(TypedDict):
    agent: Literal["researcher", "coder", "analyst", "__end__"]

# ======================
# 2. 状态定义
# ======================
class RouterState(TypedDict):
    messages: Annotated[list, add_messages]
    next_agent: str  # supervisor 决定的下一个节点

# ======================
# 3. 初始化模型
# ======================
model = ChatOpenAI(model="gpt-3.5-turbo")

# ======================
# 4. Supervisor 节点 — LLM 分析意图，输出结构化路由决策
# ======================
def supervisor_node(state):
    response = model.with_structured_output(RouteDecision).invoke(
        "分析以下请求，决定发送给哪个专家：" + str(state["messages"])
    )
    return {"next_agent": response["agent"]}

# ======================
# 5. 路由函数 — 读取 supervisor 的决策，返回目标节点名
# ======================
def router(state) -> Literal["researcher", "coder", "analyst", "__end__"]:
    return state["next_agent"]

# ======================
# 6. 三个专家节点 — 各自处理不同领域的任务
# ======================
def researcher_node(state):
    return {"messages": [{"role": "assistant", "content": "我是研究员，负责查资料"}]}

def coder_node(state):
    return {"messages": [{"role": "assistant", "content": "我是程序员，负责写代码"}]}

def analyst_node(state):
    return {"messages": [{"role": "assistant", "content": "我是分析师，负责数据分析"}]}

# ======================
# 7. 构建工作流
# ======================
workflow = StateGraph(RouterState)

# 添加节点
workflow.add_node("supervisor", supervisor_node)
workflow.add_node("researcher", researcher_node)
workflow.add_node("coder", coder_node)
workflow.add_node("analyst", analyst_node)

# 设置起点
workflow.set_entry_point("supervisor")

# 条件路由 — supervisor → 各专家 或 END
workflow.add_conditional_edges(
    "supervisor",
    router,
    {
        "researcher": "researcher",
        "coder": "coder",
        "analyst": "analyst",
        "__end__": END,
    }
)

# 专家执行完 → 回到 supervisor 继续决策
workflow.add_edge("researcher", "supervisor")
workflow.add_edge("coder", "supervisor")
workflow.add_edge("analyst", "supervisor")

# 编译
app = workflow.compile()

# ======================
# 8. 测试运行
# ======================
if __name__ == "__main__":
    result = app.invoke({
        "messages": [{"role": "user", "content": "帮我写一个Python爬虫"}],
        "next_agent": ""
    })
    print(result["messages"][-1]["content"])
💡 Supervisor 模式 = 层次化 Agent 架构：Supervisor 本身也是一个 LLM 调用， 但它不直接回答问题，而是输出结构化的路由决策。各子 Agent 可以完全独立开发、独立部署， 甚至可以由不同的模型驱动（如：coder 用 Claude Opus，researcher 用 GPT-4 + 搜索工具）。 这是构建复杂 AI 助手（如 Copilot、客服系统）的核心模式。

4. Human-in-the-Loop — 人机协作中断与审批

LangGraph 提供 interrupt（中断） 机制，允许在图的特定节点之前暂停执行， 等待人工审批或输入后再继续。这在需要安全审查、人工确认的关键环节（如：发送邮件、执行数据库写操作、调用付费 API）至关重要。

# Human-in-the-Loop: 在敏感节点前中断
app = workflow.compile(
    interrupt_before=["send_email", "execute_sql"]
)

# 执行到中断点
for event in app.stream(initial_state):
    print(event)

# 获取当前状态，等待人工审批
state = app.get_state(config)
print(state.values["pending_action"])  # 展示待审批操作

# 人工审批通过后，继续执行
app.update_state(config, {"approved": True})
for event in app.stream(None, config):  # None = 从当前状态继续
    print(event)
💡 中断 ≠ 暂停线程：LangGraph 的中断是通过检查点（Checkpoint）实现的。 当中断发生时，图的当前状态被序列化保存到持久化存储（如 SQLite、Postgres）。 这意味着审批者可以在数小时后回来审批，系统可以从检查点无缝恢复执行。 这是生产级 Agent 系统的关键特性。

5. 检查点与时间旅行 — Agent 的"存档/读档"

LangGraph 在每个 super-step（一个节点执行完成）后自动保存检查点。 检查点包含完整的 State 快照。这解锁了强大的能力： 时间旅行（回退到历史状态重新执行）、分支（从历史状态 fork 出不同路径）、 重放（用不同参数重新执行历史的某个步骤）。

💡 检查点是 LangGraph 最被低估的能力：它不仅支持人机协作（中断→人工审批→继续）， 还能实现 A/B 测试（从同一起点 fork 出不同策略路径对比结果）、 自我改进（检测到错误后回退到出错前的状态，换个工具重试）、 调试与可解释性（完整回溯 Agent 的每一步决策过程）。 这一切因为 State 是普通 Python dict —— 完全可序列化、可审查、可修改。

6. 高级图模式：并行、Map-Reduce 与嵌套图

LangGraph 支持更复杂的图拓扑结构，使多 Agent 协作成为现实。 以下展示三种进阶模式及其 Mermaid 图解。

🔀 Fan-out → Parallel → Fan-in — 并行分发与汇聚

一个节点返回列表后，LangGraph 自动 fan-out：为列表中每个元素创建独立执行分支， 各分支并行执行后续节点，最后 fan-in 汇聚结果。

💡 Send API 是 LangGraph 实现 fan-out 的关键。 节点返回 Send(node_name, arg) 对象列表，LangGraph 就会为每个 Send 创建并行分支。 相比 ThreadPoolExecutor 手动管理，Send API 是声明式的、自动支持检查点和错误恢复。

💻 Fan-out / Fan-in 代码示例


from typing import Annotated, TypedDict
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.constants import Send

# 1. 定义全局状态和子任务状态
class OverallState(TypedDict):
    topics: list[str]
    results: Annotated[list[str], operator.add]  # fan-in 汇聚

class SearchState(TypedDict):
    topic: str  # 每个并行分支的独立状态

# 2. 准备任务列表 — fan-out 的起点
def prepare_topics(state: OverallState):
    return {"topics": ["AI Safety", "Blockchain", "Quantum"]}

# 3. 单个搜索节点 — 每个 topic 并行执行
def search_topic(state: SearchState):
    return {"results": [f"[{state['topic']}] 搜索结果..."]}

# 4. 汇聚节点 — fan-in 合并所有并行结果
def gather_results(state: OverallState):
    return {"results": ["\\n\\n".join(state["results"])]}

# 5. 条件路由 — Send API 创建并行分支
def fanout_router(state: OverallState):
    return [Send("search_topic", {"topic": t}) for t in state["topics"]]

# 6. 构建图
builder = StateGraph(OverallState)
builder.add_node("prepare_topics", prepare_topics)
builder.add_node("search_topic", search_topic)
builder.add_node("gather_results", gather_results)
builder.add_edge(START, "prepare_topics")
builder.add_conditional_edges("prepare_topics", fanout_router)
builder.add_edge("search_topic", "gather_results")
builder.add_edge("gather_results", END)
graph = builder.compile()

🗺️ Map-Reduce — 分而治之的评估模式

Map 阶段：将大任务拆分成独立子任务并行处理。 Reduce 阶段：汇总子结果，进行全局综合。 典型应用：长文档问答（每段独立回答 → 综合）、代码审查（每文件独立审查 → 汇总报告）。

💻 Map-Reduce 代码示例：Send API 并行处理


from typing import Annotated, TypedDict
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.constants import Send

# 1. 定义整体状态和子任务状态
class OverallState(TypedDict):
    topics: list[str]
    essays: Annotated[list[str], operator.add]  # Reduce 汇聚

class EssayState(TypedDict):
    topic: str  # 每个 Map 分支的独立输入

# 2. Map 阶段 — 拆分为独立子任务
def generate_topics(state: OverallState):
    return {"topics": ["Transformer", "GAN", "Diffusion"]}

def generate_essay(state: EssayState):
    """每个 topic 独立并行执行 (Map)"""
    return {"essays": [f"[{state['topic']}] 核心原理: ..."]}

# 3. Reduce 阶段 — 汇总所有子结果
def gather_essays(state: OverallState):
    combined = "\\n\\n".join(state["essays"])
    return {"essays": [combined]}

# 4. Send API: 动态创建并行分支
def continue_to_essays(state: OverallState):
    return [Send("generate_essay", {"topic": t}) for t in state["topics"]]

# 5. 构建图
builder = StateGraph(OverallState)
builder.add_node("generate_topics", generate_topics)
builder.add_node("generate_essay", generate_essay)
builder.add_node("gather_essays", gather_essays)
builder.add_edge(START, "generate_topics")
builder.add_conditional_edges("generate_topics", continue_to_essays)
builder.add_edge("generate_essay", "gather_essays")
builder.add_edge("gather_essays", END)
graph = builder.compile()

🪆 嵌套子图 — 图即节点，节点即图

LangGraph 支持将一张图作为另一张图的一个节点（Subgraph）。 子图有自己独立的内部状态空间，父图只看到子图的输入和输出。 这实现了真正的模块化 Agent 架构。

💻 嵌套子图代码示例：子图作为父图节点


from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode
from langgraph.graph.message import add_messages

# ========== 1. 子图：ReAct Agent ==========
class SubAgentState(TypedDict):
    messages: Annotated[list, add_messages]

def agent_node(state: SubAgentState):
    """LLM 分析 + 决策（可使用任意工具）"""
    response = model.bind_tools(tools).invoke(state["messages"])
    return {"messages": [response]}

def route_tools(state: SubAgentState):
    last_msg = state["messages"][-1]
    return "tools" if last_msg.tool_calls else "__end__"

sub_builder = StateGraph(SubAgentState)
sub_builder.add_node("agent", agent_node)
sub_builder.add_node("tools", ToolNode(tools))
sub_builder.add_edge(START, "agent")
sub_builder.add_conditional_edges("agent", route_tools)
sub_builder.add_edge("tools", "agent")
delegation_agent = sub_builder.compile()  # 子图编译为可调用组件

# ========== 2. 父图：编排层 ==========
class ParentState(TypedDict):
    task: str
    sub_result: str
    final_report: str

def delegate_to_agent(state: ParentState):
    """将任务委托给子图 — 子图作为节点运行"""
    result = delegation_agent.invoke({"messages": [state["task"]]})
    return {"sub_result": result["messages"][-1].content}

def generate_report(state: ParentState):
    return {"final_report": f"综合报告:\\n{state['sub_result']}"}

# ========== 3. 父图构建 ==========
parent = StateGraph(ParentState)
parent.add_node("delegation_agent", delegate_to_agent)  # 子图即节点
parent.add_node("generate_report", generate_report)
parent.add_edge(START, "delegation_agent")
parent.add_edge("delegation_agent", "generate_report")
parent.add_edge("generate_report", END)
app = parent.compile()

# 运行：app.invoke({"task": "分析 Transformer 注意力机制"})

7. LangChain vs LangGraph — 何时用哪个？

LangChain 和 LangGraph 不是竞争关系，而是 互补关系。 LangChain 提供组件（LLM、工具、检索器）和简单管道； LangGraph 提供复杂控制流（循环、分支、并行、人机协作）。 两者可以混合使用：在 LangGraph 的节点内使用 LangChain 的组件。

维度 LangChain LangGraph
核心抽象 Runnable / Chain StateGraph（有向图）
数据流 单向、无环（DAG） 任意有向图（含循环）
执行模型 管道串联（| 运算符） 状态机转移（节点→节点）
条件分支 有限（RunnableBranch） 一等公民（条件边）
循环 不支持 原生支持
并行 有限（RunnableParallel） Send API Fan-out/Fan-in
持久化 / 检查点 无内置支持 内置 Checkpointer（SQLite/PG）
Human-in-the-Loop 需自行实现 interrupt / update_state 原生支持
时间旅行 不支持 get_state_history + fork
流式输出 .stream() / .astream() .stream() 含节点级事件
适用场景 简单 RAG、单次 LLM 调用链 Agent 循环、多 Agent 协作、人机审批
底层依赖 自包含 依赖 langchain-core（Runnable 协议）
💡 最佳实践：大多数生产级 LLM 应用最终都会使用 LangGraph，因为现实的 Agent 场景几乎都需要循环和条件判断。 但 LangGraph 节点内部仍然大量使用 LangChain 的组件（ChatModel、Tool、PromptTemplate 等）。 关键是理解两者的分工：LangChain 提供"做什么"（组件），LangGraph 定义"何时做"（控制流）。
