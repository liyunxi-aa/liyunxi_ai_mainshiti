🔌 MCP · Model Context Protocol

连接 AI 模型与外部世界的开放协议 — 标准化的 Tool / Resource / Prompt 协议，让 LLM 像 USB-C 一样即插即用任何数据源与工具

1. 问题：LLM 的孤岛困境与 MCP 解法

传统方式下每个 LLM 应用需要逐个适配 API，形成 M×N 集成爆炸。 MCP (Model Context Protocol) 是 Anthropic 发布的开源协议，定义标准化的 Client-Server 接口， 让任何 MCP Server 都能被任何 MCP Client 发现并使用 — 变 M×N 为 M+N。

💡 类比：MCP 之于 AI 工具集成，如同 USB-C 之于外设连接。 在 MCP 之前，每个 AI 应用需要为 GitHub、Slack、数据库等各自写特殊适配器； 有了 MCP 后，只需实现一次 MCP Server，所有 MCP 客户端都能即插即用。

2. 三层架构：Host → Client → Server

MCP 采用三层架构：MCP Host（承载 AI 模型的应用）、MCP Client（协议客户端，与 Server 1:1 连接）、 MCP Server（暴露 Tools/Resources/Prompts 的服务端）。Host 可管理多个 Client，每个 Client 连接一个 Server。 支持本地 (stdio) 和远程 (HTTP SSE) 两种传输方式。

💡 关键设计：1 Client = 1 Server，非多路复用。每个 MCP Server 是独立进程（或远程服务）， Client 通过 stdio 或 HTTP 与之通信。Host 可以同时运行多个 Client，给 AI 模型提供来自不同来源的工具和数据。

3. 三大核心原语：Tool · Resource · Prompt

MCP Server 通过三种标准化原语向 AI 模型暴露能力，每种原语在 JSON-RPC 协议中有明确的请求/响应结构。

🔧

Tools 工具

模型可执行的操作。类似函数调用 — 模型决定何时调用、传什么参数，Server 执行并返回结果。
例: search_code, create_issue, run_query

📦

Resources 资源

模型可读取的结构化数据。类似 REST GET 端点 — 通过 URI 标识，支持 text 和 binary 两种内容类型。
例: file://doc.txt, db://schema/users

💬

Prompts 提示模板

预定义的交互模板。Server 声明结构化 prompt 列表，用户选择后填充参数，生成标准化的对话起始。
例: "Summarize this code"、 "Review this PR"

🧠

Sampling 采样 (Server→Client)

Server 可反向请求 LLM 生成内容。允许工具内部嵌套 AI 推理 — 如代码审查工具调用模型生成 review 意见。
例: summarize → LLM → embed → store

📐 JSON-RPC 消息格式 (基于 JSON-RPC 2.0)

💡 双向能力：前三个原语是 Client→Server 方向（AI 模型调用工具、读取数据、使用模板）； Sampling 是 Server→Client 方向（Server 反向请求模型推理），让 MCP 支持嵌套的 AI 工作流。

4. 协议生命周期：Initialize → Message Exchange

MCP 通信基于 JSON-RPC 2.0。首先进行能力协商 (Initialize)，双方声明各自支持的功能； 随后进入消息交换阶段，Client 可发送 tool/resource/prompt 相关的 request/notification。

1→ 2→ 3→ 4→ 5→ 6 Initialize 请求
Step 1: Initialize (能力协商) — Client 发送自身能力声明 (协议版本、支持的传输方式)， Server 返回自身能力 (可用的 tools/resources/prompts/sampling) 及服务器指令 (instructions)。
💡 能力协商的核心价值：Client 和 Server 各自声明功能后，双方都清楚对方的能力边界。 这意味着 AI 模型能动态发现可用的 Tools 和 Resources（而非硬编码），实现了真正的即插即用。

5. 传输层：stdio vs Streamable HTTP

MCP 支持两种传输协议，分别适用于不同场景。stdio 适用于本地工具（启动子进程）， Streamable HTTP 适用于远程服务（HTTP POST + SSE 事件流）。两者在消息格式上统一使用 JSON-RPC。

特性 stdio (标准输入输出) Streamable HTTP (HTTP + SSE)
适用场景 本地工具 / 命令行程序 远程服务 / 云端 API
连接方式 Client 启动 Server 子进程 HTTP POST 请求 + SSE 流
发现机制 命令行参数指定 URL 端点 + DNS 解析
安全性 进程隔离 (本地) 需要 OAuth / API Key 认证
延迟 极低 (本地 IPC) 受网络条件影响
部署复杂度 低 (单机) 需要部署 + 运维
多租户支持 不支持 (进程级) 支持 (服务端多路复用)
编程语言要求 任何语言 (独立进程) 任何语言 (HTTP 服务)
💡 选择建议：本地开发 / 个人工具用 stdio（简单、零配置）； 生产环境 / 团队共享用 Streamable HTTP（可扩展、可认证、可监控）。 Claude Desktop 目前主要使用 stdio 模式，而 Anthropic Managed Agents 平台使用 Streamable HTTP 连接远程 MCP Server。

6. MCP vs 传统 Function Calling — 范式对比

MCP 不只是 "另一种 function calling 格式"。传统 function calling 是调用侧的协议（模型输出工具调用）， 而 MCP 是完整的服务端协议 — 涵盖工具发现、资源读取、提示模板、认证、传输等。

维度 传统 Function Calling MCP (Model Context Protocol)
协议层级 API 调用侧 (模型 → 工具) 完整应用层协议 (Host ↔ Client ↔ Server)
工具发现 开发者硬编码 tool schema Server 动态声明 tools/list
数据类型 仅工具调用 Tools + Resources + Prompts
认证机制 无标准 (各平台自定) OAuth 2.0 + API Key (标准化)
传输协议 耦合于 LLM API 独立传输 (stdio / HTTP)
反向调用 不支持 Sampling (Server→Client LLM 请求)
生态系统 封闭 (每个平台自建) 开放 (开源 + 社区 Server 市场)
提示模板 不支持 prompts/list + prompts/get
资源读取 无标准 resources/list + resources/read (URI 标识)
💡 本质差异：Function Calling 只是 LLM API 的输出格式（"我想调用这个函数，参数是…"）； MCP 是完整的连接协议（"我发现你有这些能力，我要用其中这个，请执行并返回结果"）。 这就是为什么 MCP 能构建开放的 Server 市场 — 任何 MCP Server 实现都能被任何 MCP Client 消费。

7. 实战示例：天气查询 MCP Server (Python)

下面展示一个完整的 MCP Server 实现 — 暴露 get_weather 工具和 config://city 资源。 Server 通过 stdio 传输与 Client 通信，使用 MCP Python SDK 快速构建。

# weather_server.py — MCP Weather Server from mcp.server import Server, stdio_server from mcp.types import Tool, TextContent, Resource # 1. 创建 Server 实例 server = Server("weather-server") # 2. 注册 Tool — get_weather @server.list_tools() async def handle_list_tools() -> list[Tool]: return [ Tool( name="get_weather", description="获取指定城市的当前天气", inputSchema={ "type": "object", "properties": { "city": {"type": "string", "description": "城市名称"}, }, "required": ["city"], }, ) ] @server.call_tool() async def handle_call_tool(name: str, args: dict): if name == "get_weather": # 实际应用中可调用天气 API weather_data = {"北京": "22°C 晴", "上海": "25°C 多云"} city = args["city"] return [TextContent(type="text", text=f"{city}: {weather_data.get(city, '暂无数据')}")] # 3. 注册 Resource — city 列表 @server.list_resources() async def handle_list_resources(): return [Resource(uri="config://supported-cities", name="支持的城市列表")] @server.read_resource() async def handle_read_resource(uri: str): return [TextContent(type="text", text="北京, 上海, 广州, 深圳, 杭州")] # 4. 启动 (stdio 传输) async def main(): async with stdio_server() as (read_stream, write_stream): await server.run(read_stream, write_stream, server.create_initialization_options())
# mcp_client.py — MCP Client 使用示例 from mcp import ClientSession, StdioServerParameters from mcp.client.stdio import stdio_client async def run(): # 1. 启动 MCP Server 子进程 (stdio 模式) server_params = StdioServerParameters( command="python", args=["weather_server.py"], ) async with stdio_client(server_params) as (read, write): async with ClientSession(read, write) as session: # 2. 初始化连接 (能力协商) await session.initialize() # 3. 列出可用工具 tools = await session.list_tools() print(f"可用工具: {[t.name for t in tools.tools]}") # 4. 调用工具 result = await session.call_tool("get_weather", {"city": "北京"}) print(f"查询结果: {result.content[0].text}") # 5. 读取资源 resources = await session.list_resources() content = await session.read_resource("config://supported-cities") print(f"支持的城市: {content.contents[0].text}")
# claude_desktop_config.json # 路径: ~/Library/Application Support/Claude/claude_desktop_config.json { "mcpServers": { "weather": { "command": "python", "args": ["/absolute/path/to/weather_server.py"], "env": { "API_KEY": "your-weather-api-key" } }, "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"], "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "your-github-token" } } } } # 重启 Claude Desktop 后，AI 模型即可自动发现并调用 weather 和 github Server 的工具
